# Scene 联调与归档流程

先找已有动作，再补缺失能力。运行定义统一保存在业务项目的 `.flutter-pilot/scenes.json`；[动作目录](scene-actions-catalogue.md) 提供示例入口，[格式指南](workflows.md) 解释配置，[MCP 指南](mcp.md) 解释工具。本文将 Wali 登录联调中验证过的做法整理成可重复流程。

Agent 在 MCP 初始化时收到功能及任务路由说明，也可通过 `prompts/get` 读取 `capabilities` 查阅能力。已有业务操作读取 `scene_action_quick_run`，编写归档读取 `scene_action_authoring`；当前 App 截图读取 `app_screenshot` 或 `screenshot` 指南。`overview.capabilityRoutes` 提供相同的用户任务到工具映射，具体工具还有同名 Prompt 和生产参数 schema。Prompt 可离线按需读取，初始化不会全量读取模板，读取本身不执行操作；实际运行时才选择项目、设备和操作。

仅截图或查阅能力不进入下方 Scene 流程。目标是当前 Flutter App 的“截图／截屏／screenshot／长截图／布局对比”时，优先使用 Flutter Pilot：普通图直接 `take_screenshot({sessionId,source:"flutter",mode:"screen"})`，无需 Key、Scene、Mock 或 Appium；长图才先 `list_screenshot_targets` 明确区域，会实际滚动并尝试恢复。包含键盘或系统 UI 时需已绑定设备，使用 `source=device,mode=screen`。桌面和网页等其他对象使用对应工具；目标不明时先确认。只截图不重启、不导航、不切换 Mock，只启动任务确认启动结果即可。

## 优先走已有操作

| 阶段 | 操作                                                                                        | 继续条件                                                    |
| ---- | ------------------------------------------------------------------------------------------- | ----------------------------------------------------------- |
| 发现 | `list_sessions` 选择准确项目；`list_scenes` → `list_scene_actions` 找名称、前提、参数和 Key | 确认操作来源与所需 Mock，避免读取整份响应正文               |
| 启动 | 复用正确设备上的已有 Debug 会话；未运行才 `start_app` 选择已保存配置                        | 超时先查 `list_sessions` 和 IDE，不重复启动                 |
| 环境 | 配置有修改时 `reload_rules`；按任务激活 Mock，检查相关域及已接入 Dio 数                     | 所需客户端已接入；无关 WS 等域不阻塞                        |
| 运行 | 记录请求时间 / ID 基线，显式 `run_scene_action` 并保存 `runId`                              | 插件自动执行已保存步骤，不逐步截图或重新调用模型            |
| 确认 | `get_scene_action_run` 至终态，再核对最终 Key 与本轮网络；需要时取消                        | 最终 UI、请求和 Mock 命中符合目标；业务测试以 `passed` 为准 |
| 归档 | 更新原 Scene action、目录和验收边界                                                         | 定义可编译、可复用，配置中无临时运行信息                    |

没有修改配置且运行时已就绪时，不必反复重载或重新激活。纯操作也可以不激活 Mock；跨 Scene 运行公共操作保留当前 Mock。激活、reload、重连和重开 IDE 不会自动执行 UI。

可直接交给 Agent 的任务描述：

> 在指定模拟器上复用或启动此项目的 Debug 配置，激活指定 Mock，按名称执行已保存的 Scene 操作。先查动作参数和起始页面；完成后确认主页 Key 和本轮网络命中，报告预期失败 Mock 与未验证范围。

## 没有合适动作时

先读业务项目规范，确认源码拥有包和当前页面。用一次结构化快照确认真实 Key 和交互区域，只针对缺失或歧义目标查询；视觉验收再截图。检查是否已有开发入口和 API 客户端，不从 VM 连接成功推断 Mock 全覆盖。

Flutter 目标保存为 `{ "source": "flutter", "key": "emailEntry.input" }`，步骤用 `target:"emailInput"` 引用。定位链是别名 → 所属 Scene 的稳定 Key → 当前挂载控件；内部仍做 Key 匹配，Agent 无需再探索，也不缓存跨页面 Widget 对象。文字、语义和祖先是显式选择器能力，不能在 Key 失败时静默代替。

缺 Key 时在获准修改的源码加 `ValueKey<String/int>`，确认唯一、可见、启用及实际指针接收。页面根 Key 适合等待；按钮 Key 适合点击；输入框 Key 对应唯一编辑器。复合底栏可能有可见图层和选中副本，应让 Key 跟随当前可见交互层，避免重复和裁剪。不要借全页收键盘手势把普通区域误认成按钮。

保存操作时：

- 描述起始页面、登录状态、参数、终点和所需 Mock；首次登录、最近账号页、已有登录会话分别提供入口。
- 通用表单 / 验证码 / 返回主页步骤放公共操作 Scene，入口通过 `call` 和显式参数映射复用。只保留一份通用步骤，保持对外 action ID 稳定。
- 输入使用字符串参数；密码、验证码声明 `secret:true`，公共操作和入口都保持秘密属性。不记录真实凭据、认证 VM 地址或运行 sessionId。
- 用 `wait_for_widget` 等待页面可见或按钮可操作。输入导致键盘改变布局时，`hide_keyboard` 确认收起，再等待下一控件；不用固定延时掩盖时序。
- 预检整份配置、引用、参数和展开限额，再运行。对动作整理前后的入口，比较展开后的工具、选择器和参数，避免只校验 JSON 能解析。

## 网络验证和阻塞处理

`reload_rules` 成功只表示配置被加载；域 `applied` 只表示运行时同步；操作 `completed` 只表示步骤完成。每次触发前建立新请求基线，查询本轮 method / path / status / mocked / ruleId，再看最终 UI。分页历史只输出本轮唯一接口摘要，避免刷新循环把有效证据淹没。相关接口较多时按路径查验，不用旧成功记录代替。

| 现象                       | 处理                                                                                           |
| -------------------------- | ---------------------------------------------------------------------------------------------- |
| `start_app` 超时           | 查已有会话、编译状态和 IDE 诊断；不得立即再次启动                                              |
| Key 缺失、重复、不可操作   | 检查失败步骤、当前页面、真实 Key、禁用及遮挡；修复后明确决定是否重跑                           |
| 输入后按钮偶发点不到       | 确认键盘收起和控件稳定状态，保持 Key 对应区域的实际点击位置                                    |
| HTTP 已应用但请求未 Mock   | 核对本轮 path / host / method、Dio 接入、惰性客户端和首请求窗口                                |
| 401 → refresh → 重复请求   | 停止触发或结束本轮后台重试，读实际漏接口，补齐认证后目录、资产及后台初始化链路后重载；不清数据 |
| 未确认、取消或断线         | 先查询终态和本轮业务结果；不自动再次点击提交、不换通道重放                                     |
| 测试通过但实际 VM 注入失败 | 在实际注入库 imports 和业务 SDK 上验证模板，检查公开类型是否可见                               |

Mock 使用假 token 时，登录后的账号详情、地址、组合、通知、目录和恢复任务也可能请求后端。先沿真实调用链盘点，再用新请求补漏；原规则、WS 和其他场景必须保留。提前创建正式 Dio 客户端可改善 UI 操作前的接入，但不保证启动首请求全部被拦截。

有意模拟的失败必须在 Scene 说明和验收记录中可见。例如 Wali 当前登录 Scene 的地址 probe 明确 Mock 503 并退避，保留本地钱包；这不是漏 Mock，也不代表完整地址恢复已验证。不能为消除报错而构造假的恢复成功或跳过正式认证。

## 归档和回归

动作定义保存在业务 `scenes.json` 的公共操作 Scene；可复用模式整理进 [随包示例](../resources/example.scenes.json)，仅作为新项目的模板，不是业务项目的第二配置来源。[动作目录](scene-actions-catalogue.md) 只索引 ID、前提、参数和验证状态，不复制步骤或生成运行 catalogue。Test Case 继续在 `tests.json` v2 负责环境与断言。

协议和示例用生产 `validateSceneDocument` / `compileSceneAction` 校验。重构保持展开后的原子行为不变，并确认公共操作没有修改 `activeSceneId`；适当验证 secret 传播与执行锁。工作台涉及布局或操作交互时补相应 UI 回归；VM 模板变化同时验证真实注入上下文。

交付记录分别注明 schema / 单元验证、模拟器实际流程、真实设备和未覆盖业务，不把某次成功耗时当作性能保证。本轮 Wali 登录 15 步、工作台手动返回主页 4 步与网络验证记录见 [验收记录](validation.md)；历史证据不代替未来改动后的复验。
